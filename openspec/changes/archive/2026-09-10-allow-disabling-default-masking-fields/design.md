## Context

参见 [proposal.md](./proposal.md) 的变更动机。当前公共类型将 `SensitiveFieldConfig` 定义为 `Record<string, string>`；配置加载阶段要求每个字段值都是字符串并立即校验模板，运行期则先注册全部内置策略，再用自定义模板覆盖同名策略。`LoggerFactory` 在初始化时只构造一个脱敏器，所有命名 Logger、Console 和 File 输出共享该不可变策略快照。

本变更涉及公共 TypeScript 类型、YAML 配置协议和敏感数据输出，必须保持未显式退出时的默认安全行为，并明确新配置与旧版运行时的部署边界。行为要求见 [logger-sensitive-field-masking spec](./specs/logger-sensitive-field-masking/spec.md)。

## Goals / Non-Goals

**Goals:**

- 在现有字段策略映射中表达单字段显式退出，不增加第二套容易冲突的配置集合。
- 保持字符串模板、字段名规范化、递归复制、全局开关和初始化失败时机不变。
- 使公共类型、YAML 解析结果和运行期策略使用同一种值模型。
- 让退出父字段时仍能递归检查其对象值中的其他敏感字段。

**Non-Goals:**

- 不提供按命名 Logger、输出通道、日志级别或单次日志调用区分的退出策略。
- 不允许通配符、路径表达式、正则表达式或按值动态判断是否脱敏。
- 不修改内置字段集合、模板语法、元数据规范化或 `message` 文本处理边界。
- 不新增运行期热更新；初始化完成后的配置继续保持不可变。

## Decisions

### 1. 使用 `false` 扩展现有字段策略值

公共签名调整为：

```ts
export type SensitiveFieldConfig = Record<string, string | false>;

export interface SensitiveMaskingConfig {
    enabled?: boolean;
    fields?: SensitiveFieldConfig;
}
```

内部有效配置同步使用 `Readonly<Record<string, string | false>>`。不新增泛型或包根导出，`fields` 的可选性保持不变。类型值只接受字符串或字面量 `false`；`true` 不代表任何策略，必须被类型系统和运行时校验拒绝。

选择 `false` 是因为它在 TypeScript 对象和 YAML 中都能紧邻目标字段表达“关闭此规则”，且能复用现有映射的大小写去重逻辑。替代方案 `excludedFields: string[]` 会形成两处字段来源，并额外引入同一字段同时配置模板和排除时的优先级或冲突规则；`null` 容易被理解为缺省或继承；新增原值占位符会把“不脱敏”伪装成模板，并可能让对象值直接绕过内部字段检查；全局 `includeDefaults: false` 的影响范围又大于当前需求。因此均不采用。

### 2. 配置加载阶段区分布尔值 false 与字符串模板

配置加载器遍历 `masking.fields` 时先校验字段名和大小写不敏感的重复项，然后按值类型处理：

- 值严格等于布尔值 `false` 时直接保存，不调用模板校验。
- 值为字符串时继续调用既有模板校验并原样保存；因此 YAML 中带引号的 `'false'` 仍是固定文本模板。
- 其他类型统一抛出配置错误，错误信息明确说明只允许字符串模板或 `false`。

解析结果继续使用冻结的无原型对象，避免改变不可变快照和特殊属性名的既有处理方式。重复判断继续基于小写规范化名称，因此 `Password: false` 与 `password: '***'` 必须在初始化阶段失败，而不是依赖遍历顺序决定结果。

### 3. false 通过删除策略实现，不引入原值透传函数

脱敏器继续先建立内置策略映射，再按用户配置顺序处理每个规范化字段名：

- 字符串模板编译为策略并通过 `set` 新增或覆盖。
- `false` 通过 `delete` 移除已有策略；如果该字段没有内置策略，则结果是安全的幂等空操作。

运行期递归复制逻辑无需新增“返回原值”的掩码函数。当某字段没有策略时，现有逻辑继续递归复制其值，因此 `password: { token: 'secret' }` 不会因外层 `password` 退出而绕过内部 `token` 的脱敏。这也保持了循环引用降级、日期转换和调用方对象不被修改的既有语义。

`masking.enabled` 仍在运行期统一决定是否查找策略；即使全局关闭，配置中的字符串和 `false` 仍会在初始化阶段完成结构与模板校验，以保持配置错误尽早暴露的原则。

### 4. 以公共输出和类型契约共同验证能力

验证分为三层：配置加载单元测试覆盖布尔值 `false`、带引号的 `'false'`、非法类型和大小写重复；脱敏器单元测试覆盖默认保护、字段退出、别名隔离以及退出父字段后的递归处理；至少一个 Console 或 File 集成测试证明最终输出遵循退出策略且输入对象未被修改。公共类型使用独立编译夹具验证字符串和 `false` 为正例，`true`、`null` 和数字为负例。

README 必须把 `masking.fields` 类型更新为 `Record<string, string | false>`，提供不加引号的 YAML 示例，并警告字段退出会全局作用于所有命名 Logger、输出通道和嵌套层级。发布记录使用 `minor` changeset，不修改当前工作区中其他 changeset。

## Risks / Trade-offs

- [错误退出真实凭据字段会把原始敏感值写入日志] → 默认策略保持不变，只有显式布尔值 `false` 才退出，并在配置文档与示例旁突出全局安全影响。
- [调用方误写 `'false'` 认为已经退出] → 明确区分 YAML 布尔值与字符串，并用解析测试和 README 示例固定行为。
- [全局字段名策略可能影响多个业务模块] → 保持当前配置作用域，不静默扩展为按 Logger 配置；文档要求调用方评估所有同名字段来源。
- [旧版 Logger 无法读取新配置] → 采用先升级包、后启用 `false` 的发布顺序；回滚前先从配置中移除所有布尔值策略。
- [公共类型联合会要求内部调用点处理 false] → 有效配置与公共配置使用同一联合类型，策略构建处通过穷尽分支集中消化差异，不把联合值传播到模板编译器。

## Migration Plan

1. 发布包含本能力的 `@jintianxiayu/logger` minor 版本；既有配置无需迁移。
2. 下游应用先升级并完成现有日志配置的启动验证，此阶段不加入 `false`，可与未升级实例并存。
3. 确认所有读取目标配置的实例都已升级后，再在 YAML 或初始化对象中为目标字段设置布尔值 `false`。
4. 回滚到旧版前，先移除配置中的所有 `false` 字段策略；否则旧版会按既有规则在初始化阶段拒绝配置。

本变更不涉及存量数据转换。若滚动部署期间新旧实例必须读取同一份配置，则在旧实例全部退出前不得启用新字段值。
